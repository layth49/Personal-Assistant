# L.A.I.T.H.49 — Personal Assistant

Voice assistant for Windows, .NET Framework 4.8.1, AnyCPU. This branch (`local-laith`) runs the AI stack entirely on the host machine.

## What the program does

1. Idles on a wake-word (`Hey 49`) detected on-device.
2. Plays a time-of-day greeting and listens for a command.
3. Either executes a built-in command (lights, weather, prayer times, SMS, PlayStation, doors, shutdown, YouTube, etc.) or falls back to the local LLM for a free-form answer.

## Local stack — what replaces what

| Subsystem | Cloud (`main`) | Local (this branch) | Default endpoint |
|---|---|---|---|
| Wake word | Azure `KeywordRecognizer` (on-device) | **unchanged** — runs against `keyword.table` | n/a |
| LLM | Gemini 2.5 Flash + Google-search grounding | LM Studio (`qwen/qwen3-4b-2507`) + SearxNG | `http://127.0.0.1:1234/v1`, `http://localhost:8080` |
| Vision (`look_at_screen`, `copy_from_screen`) | Gemini 2.5 Flash, same endpoint as the text path | LM Studio, a **separate** model — `LocalVisionModel`, default `qwen/qwen3-vl-4b` — that must be downloaded separately and competes with the router for ~6 GB of VRAM | `http://127.0.0.1:1234/v1` |
| STT | Azure Speech-to-Text | Parakeet TDT 0.6B v2 on CPU (`stt-server/`) | `http://127.0.0.1:8001` |
| TTS | Azure Neural TTS (`en-US-AndrewMultilingualNeural`) | Kokoro-FastAPI | `http://localhost:8880` |
| Mic capture (for STT) | Azure SDK | NAudio `WaveInEvent`, 16 kHz mono PCM | n/a |
| Audio output | Azure SDK internal player | NAudio `WaveOutEvent` | n/a |

See [local-stack.md](local-stack.md) for setup, verify curls, GPU budget.

## Code layout

C# at repo root:

- [Program.cs](Program.cs) — main loop. Wake word → greeting → STT → command match or LLM fallback.
- [SpeechManager.cs](SpeechManager.cs) — facade around wake-word recognizer, Whisper STT, Kokoro TTS, and the pygame speech bubble.
- [LLMClient.cs](LLMClient.cs) — `LocalLLMService.GenerateResponse(string)`. OpenAI-compatible chat call to LM Studio, fed search hits from SearxNG. `TransformTextAsync(instruction, text)` is the one-shot, historyless, unsearched twin used by `reformat_note` and by `read_notes` when a question is asked of a note. `AskAboutImageAsync(question, png)` is the vision call behind `look_at_screen` and `copy_from_screen` — an OpenAI-compatible chat whose user `content` is an array of a text part and an `image_url` data URI. It returns a `VisionAnswer`, never throws, and never hangs.
- [SearxNGClient.cs](SearxNGClient.cs) — `SearxNGService.SearchAsync(query)`. Best-effort: a SearxNG outage returns empty, the LLM still answers.
- [STTClient.cs](STTClient.cs) — `SpeechToTextService.TranscribeAsync(wavBytes)`. POSTs WAV to `/v1/audio/transcriptions`. Transcription only; the mic belongs to [ContinuousListener.cs](ContinuousListener.cs), which runs Silero VAD, endpoints utterances, and gates speaker echo (with [EchoGuard.cs](EchoGuard.cs) for the transcript half of that).
- [TTSClient.cs](TTSClient.cs) — `KokoroTTSService.SpeakAsync(text)` + `StopSpeaking()`. Patches Kokoro's streamed WAV header before NAudio plays it; `StopSpeaking()` cuts playback immediately.
- [PrayerTimesCalculator.cs](PrayerTimesCalculator.cs), [WeatherService.cs](WeatherService.cs), [Geolocator.cs](Geolocator.cs), [LightAutomator.cs](LightAutomator.cs), [PlaystationController.cs](PlaystationController.cs), [SMSController.cs](SMSController.cs), [Arduino.cs](Arduino.cs) — command handlers. They return a `ToolResult` and no longer speak for themselves; the two that still hold a turn of their own (`power_control`, `send_sms`) ask through `SpeechService.Current`.
- [WindowController.cs](WindowController.cs), [FileFinder.cs](FileFinder.cs), [ClipboardController.cs](ClipboardController.cs), [NotesService.cs](NotesService.cs) — the desktop tools: `manage_window` (one tool with an `action` enum, and deliberately **no close action** — closing is `kill_process`'s alone, so the router has one place to send it), `find_file`, `read_clipboard`/`set_clipboard`, and `add_note`/`read_notes`/`reformat_note` over plain `.md` files in `NotesDir`. Pure `System.*`, no model coupling; only `reformat_note` and a question put to `read_notes` reach the LLM.
- [FileLog.cs](FileLog.cs) — tees the console to `%APPDATA%\LAITH\logs`, one file per run, flushed per line. The app is a WinExe with no console, so without this every `Console.WriteLine` in the process goes nowhere. Started first thing in `Main`, below the bake-off early return.
- [AudioController.cs](AudioController.cs) — master volume and default-endpoint switching. `SetDefaultEndpoint(id, AudioRole)` moves ONE Windows role; `FindEndpointId(name, capture)` resolves a configured device name and **refuses an ambiguous substring match** rather than guessing, which is what a second virtual cable on this machine makes of "CABLE Input".

`CallScreening\` — answering the phone for you, end to end, on this machine's own stack: the caller's audio through Parakeet, the turn through LM Studio, the reply through Kokoro and back down the line. `screen_calls` / `end_call` / `list_calls` are registered **only when `CallScreening` is on in App.config** — a tool the model can see is a tool it will reach for, and "that feature is off" is not a useful spoken answer.

- [CallTransport.cs](CallScreening/CallTransport.cs) — `ICallTransport` and the plain data around it (`IncomingCall`, `CallRoute`, `CallLocation`, `AnswerResult`). One transport runs per process.
- [GoogleVoiceBrowserHost.cs](CallScreening/GoogleVoiceBrowserHost.cs), [CdpPage.cs](CallScreening/CdpPage.cs) — a headless Chrome on its own profile, driven over DevTools. Readiness is the presence of the "Call panel" element, **never the URL** — a page on the right URL still rang through to voicemail. Teardown closes the tab over HTTP, not CDP (`CloseAsync` on a dying page deadlocks), and kills the browser as a `taskkill /T` tree, because a surviving renderer poisons the next launch.
- [GoogleVoiceCallTransport.cs](CallScreening/GoogleVoiceCallTransport.cs) — detection and the answer/hang-up clicks. The detection JS anchors on the *buttons*, walks shadow roots, and strips the bidi marks Google wraps numbers in. `CurrentLocation()` says **why** it thinks a call stopped being live and logs the transition once; a dropped devtools socket with a call up is `Unknown`, not `None`.
- [GoogleVoiceTextSender.cs](CallScreening/GoogleVoiceTextSender.cs) — sends the message as an SMS. Waits for the bubble's `.status` to leave `Sending...`; Google renders the bubble *before* it sends, so closing the tab early kills the send.
- [PhoneLinkCallTransport.cs](CallScreening/PhoneLinkCallTransport.cs), [PhoneLinkCallController.cs](CallScreening/PhoneLinkCallController.cs), [PhoneLinkCallWatcher.cs](CallScreening/PhoneLinkCallWatcher.cs), [BluetoothHeadset.cs](CallScreening/BluetoothHeadset.cs) — the other transport, over FlaUI/UIA. Which buttons the toast offers depends on whether a Bluetooth headset is connected to the PC, so the route is read, never assumed.
- [CallAudioRouter.cs](CallScreening/CallAudioRouter.cs), [CallAudioPreflight.cs](CallScreening/CallAudioPreflight.cs) — moves the Windows audio roles onto the virtual cables for the call's duration, saves the originals to `%APPDATA%\LAITH\callaudio.json` and puts them back, including after a crash. Preflight plays a tone down each leg and measures what comes back, because every way this fails sounds identical from outside. `CallAudioPreflight.cs` is this branch's own file: it holds `CallAudioFormat`, `MonoResampler` and `CallAudioProbe`, which upstream live inside the conversation half's audio bridge.
- [CallLog.cs](CallScreening/CallLog.cs) — `%APPDATA%\LAITH\calls.json`. **Read the `ending` field first when a call drops** — three unrelated causes look identical from outside.
- [MessageDelivery.cs](CallScreening/MessageDelivery.cs) — texts a taken message immediately and speaks it when you are back, with one `Delivered` flag between them so you never get both.
- [CallPersona.cs](CallScreening/CallPersona.cs), [CallTools.cs](CallScreening/CallTools.cs) — the system prompt and the four-tool allow-list. The caller is an untrusted speaker: `CallTools` is built by name, fails closed to take-a-message-and-hang-up, and is never handed the real registry.
- [CallOutcome.cs](CallScreening/CallOutcome.cs) — `CallOutcome`, `CallEnding`, the transcript line and `ArmRefusal`. This branch's own file, holding the plain data the conversation half would otherwise keep hostage.
- [CallWidgetHost.cs](CallScreening/CallWidgetHost.cs) — the floating call card. The browser is headless, so without it a screened call is invisible.
- [CallScreeningService.cs](CallScreening/CallScreeningService.cs) — arms, answers, hushes, greets, converses, hangs up, restores. The order is the whole file: route BEFORE the answer, nothing spoken until the transport re-confirms the call is on the PC, headset back BEFORE the audio roles, hang up BEFORE the roles go back. Rebuilt from upstream against this stack.
- [CallAudioBridge.cs](CallScreening/CallAudioBridge.cs) — the live legs. Loopback in, virtual cable out. It emits a 20 ms frame **every 20 ms whether or not anyone is talking**, because WASAPI loopback sends *no packets at all* on an idle endpoint and an endpointer that only sees frames when there is sound can never conclude the caller stopped. Borrows `CallAudioProbe.CableWriter` rather than declaring a second encoder.
- [CallSession.cs](CallScreening/CallSession.cs) — one call's conversation, plus `CallModel`, the streamed LM Studio turn that carries the four tool schemas in the SAME request as the reply. The endpointer, the barge-in and the turn-taking are all local here; upstream a Live socket did them. **It never touches the microphone** — the caller arrives through the bridge, so nothing contends with `ContinuousListener`.
- [CallGreeting.cs](CallScreening/CallGreeting.cs) — the greeting by name, and `CallClipCache`, which renders it through Kokoro into `callclips\<voice>\<sha1-of-text>.wav`. **Keyed on voice AND text**, so changing `CallVoice`/`KOKORO_VOICE` or rewording `CallGreetingNamed` misses correctly and every caller falls back to the stock `greeting.wav` rather than being greeted in the wrong voice.

Python alongside:

- [SpeechBubble.py](SpeechBubble.py) — pygame bubble; loaded via pythonnet. Untouched by the local-stack swap.
- [SMSService.py](SMSService.py) — Phone Link automation for SMS.
- [AutoRemotePlay.py](AutoRemotePlay.py) — PS Remote Play game-launch automation.

## Environment variables

**Required:**
- `WEATHERAPI_KEY` — OpenWeatherMap key (still cloud).

**Optional (defaults shown):**
- `LMSTUDIO_URL` — `http://127.0.0.1:1234/v1` (not `localhost` — LM Studio is a host process binding IPv4 only, same trap as the STT service)
- `SEARXNG_URL` — `http://localhost:8080`
- `STT_URL` — `http://127.0.0.1:8001` (the Parakeet service; `WHISPER_URL` is still read as a fallback). Not `localhost` — see the editing notes.
- `KOKORO_URL` — `http://localhost:8880`
- `KOKORO_VOICE` — `am_onyx`
- `IP_ADDRESS:PLUG`, `IP_ADDRESS:SWITCH` — TP-Link Kasa LAN endpoints
- `CONTACTS_PATH` — JSON file mapping contact names → phone numbers
- `LAITH_ECHO_GATE` — `auto` (engage the barge-in energy gate only once speaker bleed is observed) / `on` / `off`
- `LAITH_ECHO_MARGIN` — how far above the measured speaker bleed a frame must sit to count as you talking, default `1.5`. Lower if barge-in needs shouting, raise if the assistant cuts itself off
- `LAITH_ECHO_TEXT_GATE` — `off` disables the transcript echo check (debugging only)

`SPEECH_KEY`, `SPEECH_REGION`, `SPEECH_ENDPOINT_ID`, `GEMINIAPI_KEY` are **not used** on this branch.

## Settings (`App.config`)

Everything in `<appSettings>` is read through `LaithConfig` and documented in place in [App.config](App.config) — it is deployed as `Personal Assistant.exe.config`, editable next to the exe with no rebuild. Three things to know before changing one:

- **An environment variable of the same name wins.** `LaithConfig` maps the key to a `LAITH_`-prefixed SCREAMING_SNAKE name (`LocalVisionModel` → `LAITH_LOCAL_VISION_MODEL`) and reads that first. A stale one in `HKCU:\Environment` silently ran this app on the wrong model for weeks.
- **`LaithConfig.Dump()` prints what actually took effect**, marking each value `(env)`, `(config)` or `(default)`. That `[config]` line is the first thing to read when a setting appears to do nothing. It runs late in `Main` on purpose: `LaithConfig` reports only what has resolved so far, and on this branch almost nothing resolves early (the notes directory arrives with `NotesService`, the presence thresholds with `PresenceGate`). Anything that resolves *after* it reports its own line — `PresenceGate` does.
- Secrets stay in the environment (`WEATHERAPI_KEY`, `CONTACTS_PATH`) and are not settings.

The vision keys, since they are the only ones naming a model:

- `LocalVisionModel` — default `qwen/qwen3-vl-4b`. **Must match a model LM Studio actually has**, id and all (`lms ls`); a wrong id is a 404 and the assistant says so out loud, naming what it tried. This is the only request the app makes that names a model at all — everything else omits `model` and gets whatever is loaded.
- `LocalVisionMaxDimension` — default `1920`. Longest edge a screenshot may reach before being resampled down.
- `LocalVisionTimeoutSeconds` — default `180`. Bounded because the microphone is held open for the whole turn.

## Editing notes

- The wake-word `KeywordRecognizer` is the only Azure Speech component still in play and it's on-device — don't remove `Microsoft.CognitiveServices.Speech` from `packages.config` or the csproj.
- `Say(userInput, response)` is the unified TTS+bubble entrypoint. It schedules the synth on the threadpool and shows the bubble in parallel; the bubble retracts when the synth completes. Prefer this over calling `SynthesizeTextToSpeech` + `SpeechBubble` separately.
- Kokoro has **no SSML**. For pronunciation control, hand the synth a spelled-out transliteration (see `PrayerTimesCalculator.PrayerSpoken`).
- **Kokoro says emoji out loud** — hand it `😊` and it pronounces "smiling face with smiling eyes". `KokoroTTSService.StripUnspeakable` removes them inside `RequestWavAsync`, the one place both the one-shot and streaming paths go through, so the bubble still shows them and the voice never says them. Don't route around it: those invented words also come back through the mic as text no reply ever contained, which is what let a whole reply escape the echo gate.
- Kokoro-FastAPI streams its WAV with placeholder RIFF/data chunk sizes that NAudio's `WaveFileReader` rejects. `TTSClient.FixWavHeaderSizes` rewrites them in-place — keep that step.
- **A note is markdown, and Kokoro reads markdown out loud.** `read_notes` speaks `Program.SpokenNoteText(content)` — headings, bullets, checkboxes, rules, emphasis and link URLs stripped — while the model still receives the note verbatim under the result's `content` fact. `main` speaks its notes raw because its voice already reads markdown as prose; here `- milk` comes out "dash milk". Emoji are a separate layer and already handled inside `KokoroTTSService.StripUnspeakable`, so this only has to deal with the ASCII markers that survive it.
- **The vision model is a SECOND model, and the VRAM budget is tight.** `AskAboutImageAsync` is the only call in the app that sends a `model` field; naming `LocalVisionModel` is what makes LM Studio load the VLM just-in-time, on a box with ~6 GB — the same constraint that ruled out a true speech-to-speech model here. Expect LM Studio to **evict the router** to load it and back again, so the first `look_at_screen` in a while is slow and so is the first spoken answer after it. Nothing is broken when that happens.
- **A vision call must fail loudly and must not hang.** `ContinuousListener` is holding the turn while it runs, so an unbounded wait is dead air with the microphone open. `AskAboutImageAsync` never throws and returns a `VisionAnswer` carrying a *speakable* reason: model not downloaded (404, and it reads the id back), LM Studio unreachable, still loading (the bounded `LocalVisionTimeoutSeconds`), or rejected. main returns a bare string and null, which is fine there because there is one way to fail; here there are four and they need four different things done about them.
- **The screenshot is downscaled before it is sent, and that is in tension with `copy_from_screen`.** Image tokens scale with area, so a 4K capture is several times the prompt of a 1080p one and on 6 GB the failure is a refused request, not a slow one — but downscaling is exactly what destroys the small text `copy_from_screen` exists to return **verbatim**. `LocalVisionMaxDimension` is 1920 so the common case is the *identity transform*: a 1080p monitor passes through unresampled, and the cap cannot be blamed for a misread character there. Only a 4K screen or `monitor:"all"` across two screens get resampled (`3840x1080` → `1920x540`, i.e. half-height text) — which is a further reason `ScreenshotService.CaptureBytes` defaults to the focused monitor. Resampling is HighQualityBicubic and re-encoded as PNG on purpose; JPEG rings around exactly the high-contrast edges being read.
- **`look_at_screen`'s answer is flattened for speech, `copy_from_screen`'s is not.** Same reason `read_notes` is: a small VLM answers in markdown however it is asked not to, and Kokoro reads `**Error:**` as "star star Error colon". `Program.FlattenMarkdownForSpeech(answer, dropLeadingHeading: false)` is `SpokenNoteText`'s shared body — `false` because a note's first heading is its own title (already said in the sentence around it) while a vision answer's leading `# 404 Not Found` *is* the answer. The verbatim text still reaches the model under the `answer` fact. `copy_from_screen` must never be flattened: its whole contract is that the characters on the clipboard are the characters on the screen. It also keeps the copied text **out of `Speech`** — it can be a stack trace — and speaks only a length summary. Both paths do get `StripWholeAnswerFence`, inside `AskAboutImageAsync`, because a ``` fence would otherwise be pasted.
- **`TransformTextAsync` is not built on `AnswerAsync`, and should not be.** No history, no `BaseSystemPrompt` (that one orders the model to avoid markdown and answer in one short sentence — the opposite of what reformatting a note needs), no search hits, not streamed. It keeps `reasoning_effort = "none"` for the same reason the router and the event judge do, and it has its **own `HttpClient`** because the shared 60s timeout is far too short for a 4096-token rewrite on this box — an abort halfway looks exactly like a refusal, and `reformat_note` would then leave the note alone every time without saying why. Small local models also fence a whole answer in triple backticks however firmly they are told not to, which would be written straight into the note; `StripWholeAnswerFence` removes only a fence wrapping the entire answer, never a code block inside one.
- **A local model will sometimes hand back a tool call as plain text** rather than through the `tool_calls` channel — most often when the tool it wants isn't registered, as `send_sms` isn't whenever `CONTACTS_PATH` fails to resolve. Streamed straight to Kokoro it gets read aloud ("…arguments, recipient, message, slash tool call"). `LocalLLMService.ToolCallStart` truncates the stream at the marker; it also catches bare `{"name": …, "arguments": …}` with no marker. When that leaves *nothing* to say the reply falls back to a spoken line — silence is the worst outcome, since the user gets no audio, no bubble, and no idea they were heard. Cases in `bakeoff/echo/ToolCallTest.cs`.
- Transcription is empty-string-on-failure. Callers check `string.IsNullOrEmpty(text)` instead of the old Azure `ResultReason.NoMatch`.
- **`SearxNGService` is best-effort for chat and load-bearing for verification, and those need opposite failure behaviour.** An outage returns an empty list so the LLM still answers from its own knowledge — right for `web_search`, and exactly wrong for "has this event happened yet", where answering from training data is the failure the feature exists to prevent. `LocalLLMService.VerifyEventAsync` therefore **refuses** on an empty result set (`EventVerdict.Unknown`) instead of falling through to the model. Consequence: a silently-broken SearxNG presents as an event watch that waits forever, never as a wrong answer. Check it with `curl 'http://localhost:8080/search?q=test&format=json'` — a 403 means the container isn't reading a `settings.yml` with `formats: [html, json]` and `limiter: false`. **Verify with `docker inspect searxng` what it actually mounted**: on 2026-08-11 the running container had been created by a `docker-compose.yml` in the *main* worktree that no longer exists, so it was mounting main's stock 70 KB settings (html only, no `limiter.toml`) while the correct config sat unread in this worktree. `docker compose` also interpolates the **whole** compose file even when you name one service, so `docker compose up -d searxng` needs `.env` (gitignored) to define `CONTACTS_FILE`.
- **`VerifyEventAsync` splits into retrieve-then-judge on purpose** (`JudgeEventAsync` is the second half, public). A SearxNG outage and a model answering in the wrong shape both surface as `Unknown`, and telling them apart is most of debugging. It also means the prompt can be tested with the search stack down — see `bakeoff/resume/`.
- **The verification call must keep `reasoning_effort = "none"`.** Same lesson as the router: a model that spends its budget thinking returns empty `content`, which parses as `Unknown`, so the watch re-checks forever and the log blames the search. `/no think` in the prompt does not do this reliably.
- **Address a local service as `127.0.0.1`, never `localhost`.** Learned on the STT service: the name resolves to `::1` first on Windows, so against an IPv4-only socket each transcription waited ~2s for the IPv6 connect to be refused — 2247 ms vs 205 ms for identical work, presenting as a slow model. Docker publishes dual-stack and hides it; anything run directly on the host does not.
- The STT service is a container built from `stt-server/` (`docker compose up -d stt`; `.\stt-server\start.ps1` runs the same thing on the host for debugging). `curl http://127.0.0.1:8001/health` and check `boost_phrases` isn't 0; 0 means `CONTACTS_PATH` didn't resolve, which costs ~33 points of contact-name recall. Compose reads that path from `.env`, the app reads it from the user environment — both have to be right.
- Contact names reach the decoder differently per engine: whisper takes them as a prompt (which `TranscribeAsync` still sends), Parakeet as a decode-time boosting tree built server-side from the same file. Both read `CONTACTS_PATH`.
- `WarmUpAudioAsync` is still needed (Bluetooth / wireless DAC startup clipping). It hits Kokoro with `.`, also pre-loading the voice model on the server side. `LocalLLMService.WarmUpAsync` is its LM Studio twin (a one-token completion — the first request after a model load is much slower); `Program.Main` runs both in one `Task.WhenAll` before the first wakeword can fire.
- **There is exactly ONE `SpeechService` — `SpeechService.Current`. Never `new` one in a handler.** Six of them used to (`LightAutomator`, `PlaystationController`, `PrayerTimesCalculator`, `SMSController`, `WeatherService` ×2) and a second instance is silently useless in both directions: its `BeginSpeaking` updates a `ContinuousListener` that was never started, so the *real* listener never learns the assistant is talking and every prompt that handler speaks escapes the echo gate wholesale; and its `RecognizeOnceAsync` waits on that same dead listener, so it always times out. Observed end to end: the SMS flow got `""` back from dictation and **actually sent an empty text to a real number**, while its escaped prompts queued as turns and the assistant held a minute-long conversation with itself. Handlers reference it through a `speechManager` property that returns `SpeechService.Current`, so there is no construction-order trap.
- **`send_sms` takes the body as an argument and reads it back before sending.** It used to dictate its own body through a second `SpeechService`, which is the bug above. `Program.HandleSendSmsAsync` speaks the question, waits one turn on `ListenForTurnAsync`, and sends only on a clear yes — silence, a correction and anything ambiguous all mean *not sent*. This is safe only because the dispatch loop awaits `DispatchAsync` before listening again, so nothing else is consuming utterances while the handler holds the turn; a handler that opened its own mic instead would deadlock the listener. The "introduce yourself" substitution happens in that handler **above** the read-back — never in `SMSControl`, or the user approves one message and another gets sent.
- **`MEDIA_PLAY_PAUSE` is a toggle, which is the wrong shape for a voice command.** `MediaController.PlayAsync`/`PauseAsync` use SMTC's explicit controls so "unpause" means unpause however many times it is asked; the key toggle survives only as a fallback, and only when the playback status was actually read (otherwise it is a coin flip, which is how three "unpause" requests in a row left the video paused). `MediaCommandResult` keeps "nothing is playing" and "the session refused" as different answers, because they are different sentences.
- **`MaxUtteranceSamples` (20s) is a CHUNK boundary, not a turn boundary.** Hitting it transcribes the audio so far and keeps recording; only silence ends a turn. It used to end the turn, so reading a long list aloud was cut mid-sentence, the fragment answered while the user was still talking, and the remainder became a second turn — one question, three bubbles. The banked chunks are stitched in `TranscribeAndPublishAsync` under `transcribeGate` (two transcriptions in flight can otherwise finish out of order). Two stranding traps the guards exist for: a tail shorter than `MinSpeechSamples` must NOT be discarded as a blip once chunks are banked, and a blank tail transcript must flush the bank rather than return. Cases in `bakeoff/echo/ContinuationSim.cs`.
- **Every path that produces assistant audio must go through `SpeechService.BeginSpeaking` / `EndSpeaking`** (they're already inside `sayGate` on all of them, so `speaking` can never be clobbered by an overlapping speaker). Skipping them is not a cosmetic omission: barge-in won't fire for that audio, and — worse — the listener won't know to echo-check what it hears, so the assistant can end up answering itself.
- **On loud speakers the wakeword is the ONLY barge-in that works** — `SpeechService.StartWakewordWatch` runs the on-device spotter for the length of every streamed reply, so saying `49` cuts it. The level gate can't help there and neither can the text gate: once the mic hears the assistant continuously the VAD never gets a gap, so the whole reply arrives as ONE utterance with the user's interruption buried in it, and the echo check drops the lot. Text can't separate them either, because a reply reuses the question's own vocabulary ("tell me how a jet engine works" vs a reply opening "A jet engine works by…" is a verbatim four-word run). Two things this needs: `replyNamesAssistant` suppresses the trigger while the reply itself says "49"/"Laith" (otherwise it cuts itself off), and `ContinuousListener.RestartCapture()` drops the mid-capture buffer on a wakeword cut, or the command *after* the wakeword gets dropped as part of the echo it's glued to.
- **Echo handling is two independent layers, and both are load-bearing.** On speakers, Kokoro's output reaches the mic; without help the VAD fires, barge-in cuts the reply, the echo is transcribed, and answering it makes more audio to hear.
  1. `ContinuousListener`'s energy gate — while the assistant is audible, a frame only counts as barge-in if it's ≥`BargeInMargin` (1.5, `LAITH_ECHO_MARGIN`) above a **decaying peak** of the bleed. A peak, not an average: an average sits mid-dynamics, so the assistant's own loud syllables clear it. Two things about it are non-obvious and were both learned the hard way:
     - **The gate keys off `KokoroTTSService.PlaybackStarted`, never off the microphone.** Deriving "the speakers are on" from the mic level always loses a race it can't win: Silero recognises the assistant's voice before the frame level has risen far enough to be told apart from room noise, so the gate was still inactive when the echo's onset fired — and that happens at *any* volume, which is why turning the speakers down didn't help. The TTS knows the answer exactly; it reports it.
     - **Warm-up and the bleed measurement are anchored to when audio is AUDIBLE**, which is separate again: a streamed reply starts playing 1-2s after `BeginAssistantSpeech` (LLM → synth → playback lead), and playback itself precedes sound at the mic by a device buffer. Counting from `BeginAssistantSpeech` ran the whole calibration window in silence — it measured a "bleed peak" of 0.0089 against a room of 0.0010.
     - **The test runs on every frame of the utterance, not just its onset**, and needs `BargeInSustainFrames` (3, ~90ms) consecutive frames over the bar. The onset frame is the first ~60ms of the first syllable — level still rising, VAD only half-convinced (measured p≈0.5-0.6 against a 0.7 bar) — so judging there rejected barge-ins no amount of extra volume would have saved. Sustain is what stops one loud syllable of bleed counting.
     - **Ambient is the room's NOISE FLOOR — a minimum tracker, never a peak.** A peak latched onto the user's wakeword, which is spoken while the listener is unarmed, so the `!inSpeech` guard protecting it was inert exactly when it was needed: ambient climbed to 0.22 and the barge-in bar (`ambient x2`) became 0.4475, beyond anything a human could clear. A minimum ignores anything loud by construction.
     - **The bar is measured over warm-up only, then carried across replies** (`sessionBleedFloor`, faded 10% per reply so turning the volume down is followed). Bleed level is a property of the volume knob, not of one reply. Three attempts at learning it *during* the reply all failed, in different ways: snapshotted at the utterance start it can't follow a reply that gets louder (floor 0.1666 vs bleed reaching 0.2596 → self-cut); tracked live it chases the user's own attack up so they never get ahead of it; taught only from below-bar frames it still chases, because the quiet leading edge of the user's speech is below the bar by definition. A sustain count is also meaningless against a moving bar, since the bar moves with you.
     It gates the `SpeechOnset` **event only** — the utterance is still captured, so a genuine barge-in the gate was too strict about is answered late rather than lost (`SpeechService.OnUtteranceReady` cuts the reply then).
  2. `EchoGuard.IsEcho` on the finished transcript — the backstop that guarantees an echo never becomes a turn. Two independent tests, because they fail on different things: content-word overlap (survives the STT reordering or dropping words) **or** a ≥4-word contiguous run (survives one garbled word tanking the overlap score — that exact case, `"Mohsin, your own personal assistant"` vs `"…your own personal assistant!"`, scored 0.75 and got answered). `IsEcho` is tried against **both hyphen readings** — the STT and the reply text disagree about where a word divides, and one extra boundary breaks the run and the overlap at once (`"to-day"` vs `"today"` scored run=3 overlap=0.33 and got answered). Both readings are needed, not one: `"forty-two"` only matches `"12:42"` while the hyphen still splits. `Tokenize` also **expands digits into the words they're spoken as** (`11:03` → `eleven oh three`), because the reply text is written and the echo comes back spoken — without it every numeric tool (clock, timers, weather, prayer times) was unprotected. The reference is a **rolling window** of the last ~800 chars spoken, NOT just the current reply: an echo is routinely still mid-capture when the next reply starts (trailing silence expires ~800ms after the audio stops), and clearing the reference there let a verbatim echo through. An utterance heard over speech and *kept* logs `[echo] kept … run=…/… overlap=…` — that's the line to read when something escapes.
  `LAITH_ECHO_GATE` = `auto` (default; layer 1 engages only once bleed has actually been observed, so a headset keeps instant barge-in and pays nothing) / `on` / `off`. `Program.Main` opens the mic **before** `WarmUpAudioAsync` on purpose: the warm-up doubles as the calibration pass, so the first reply of a session is already gated instead of interrupting itself. `LAITH_ECHO_TEXT_GATE=off` disables layer 2 — debugging only. Both layers log with an `[echo]` prefix. Re-run `bakeoff/echo/` after touching any threshold; `GateSim.cs` duplicates the constants deliberately.
- **A screened call never touches the microphone, and that is the whole of how it coexists with `ContinuousListener`.** The listener owns the mic for the process lifetime and `NextUtteranceAsync` has a single waiter slot; the call takes its caller from a WASAPI loopback in `CallAudioBridge` instead, so there is nothing to hand over. What they *do* share is the room: the call's inbound leg is a loopback on the **speakers**, so anything said out loud goes down the phone, and the mic can hear the caller coming back out of those same speakers. Three separate things cover that — the hush mutes `PresenceGate` for the call's duration (and **puts the previous deadline back** rather than unmuting, via `MuteUntil`, so a "quiet until midnight" survives a call that ends at nine), `PresenceGate` reports busy through `IsOnCall`, and `Program.Main`'s wake loop **ignores the wake word outright** while a call is up. The mute only stops what is *unprompted*; a caller who happens to say "49" is a prompt, and needs its own refusal.
- **There is no `CallModel` setting and no thinking budget** — `main` has both because it names a Live model. LM Studio serves whatever is loaded, so the call runs on the same router the desktop does; `reasoning_effort = "none"` is sent unconditionally, not configurably, for the reason every other call on this branch does it. What *is* configurable: `CallVoice`, `CallModelTimeoutSeconds` (25s, deliberately shorter than the desktop's 60 — a caller listening to a minute of nothing has hung up), `CallMaxTokens`, `CallTemperature`.
- **`CallModel.TurnAsync` streams the reply and the tool calls in ONE request.** The desktop's `DetectToolAsync`-then-`StreamResponse` pair costs a second whole generate cycle, which on a phone line lands entirely inside the gap between the caller finishing a sentence and hearing anything. Content deltas and `tool_calls` deltas are accumulated from the same stream — the latter arrive **split across frames**, keyed by `index`, with the arguments dribbling in as JSON fragments, so treating a frame as a whole call gives you `take_message("{\"mess")`.
- **The call does its own endpointing, on energy, and not with Silero.** `ContinuousListener`'s VAD is welded to the mic it owns, runs under Python's GIL, and its state is reset by `Arm()` — driving it from a second concurrent audio source would have the call and the desktop resetting each other's speech state. Energy is fair *here* specifically because the inbound leg has an AGC in front of it aiming the mean at a known target and the line's idle floor is two decades below speech (`CallSpeechFloor`); it would not be fair on the microphone. Barge-in clears a much higher bar (`CallBargeInFloor`, 300 ms) because a missed barge-in costs one sentence of waiting while a false one chops the assistant off mid-word.
- **Nothing is captured from the caller while there is audio queued for them.** The two legs are different endpoints and should never meet — but "should never" is how a call ends up transcribing its own greeting as the caller's first sentence, and the cost of being wrong is the assistant holding a conversation with itself while a stranger listens. Barge-in is the one thing that reaches through, and it cancels the turn **and** calls `ClearOutbound`; only one of the two is cosmetic.
- **The per-turn latency line is `[call] turn took Nms — [latency] stt=… llm=… tts=… first-audio=…`.** It reuses the everyday `LatencyTracker`. `first-audio` is the number that matters: caller stopped talking → first sound of the answer leaves for the line. `llm` has the synthesis time **subtracted** out of it, because the sentence callback is awaited inside the stream reader and would otherwise be counted twice and blamed on the wrong stage.
